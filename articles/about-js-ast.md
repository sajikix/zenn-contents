## 　「作って理解シリーズ」とは

「作って理解シリーズ」は JavaScript に関わるツールやライブラリのしくみを、実際に簡単な実装を行いながら理解していくシリーズです。JavaScript のツールやライブラリは多くの人に利用されているものの、実際にどのようなしくみで動いているのかを理解している人は少ないのではないでしょうか？このシリーズでは、JavaScript のツールやライブラリがどのように動いているのかを、実際に手を動かしながら学んでいきます。

シリーズ第 0 回となる今回は JavaScript においてよく使われる構文木(AST)について解説します。実際に作っていく作業は次回からなので「第０回」と銘打ってはいますが、この後個別に解説する Linter やフォーマッター、ビルドツールなどはこの記事で解説する構文木を前提に動いているものがほとんどです。これらの理解を深めるためにもまずは JavaScript における構文木の扱いとその生成について学んできましょう。

## JavaScript の Parse と AST

ソースコードを解釈し操作を加える場合、文字列のままでは扱いづらいため構文や意味の切れ目を構造化した「構文木」というデータ構造に変換することが一般的です。このような操作を構文解析と呼び、構文解析を行う処理をパーサ(構文解析器)と呼びます。

### 構文木について

構文木はソースコードから文法規則に沿って生成される木構造のデータです。ソースコードから意味のあるデータ構造にすることでソースコードのチェックや変換を行いやすくします。たとえば `const word = "hello";` という式から生成される擬似的な構文木は以下のようになるでしょう。

### AST について

構文木の中で比較的よく利用される形式として抽象構文木(Abstract Syntax Tree, AST)と呼ばれる構文木の形式があります。この AST はソースコードをパースする際に、言語として意味のない情報を取り除き意味のある情報のみに単純化した構文木です。ここでいう「言語として意味のない情報」とは、最終的にソースコードの意味を解釈する上で必要にならない以下のような情報のことを指します。

- 空白
- 改行
- 木構造から明白な括弧などの記号
- ソースコード上の位置
- コメント

### JS の AST バリエーションと ESTree

JavaScript のツール群において AST が広く一般的に使われていることはわかりましたが、JavaScript の AST に対して明確なルール・仕様のようなものはあるのでしょうか？残念ながら JavaScript 自体の標準仕様はあっても、標準化団体が策定するような厳密な JavaScript の AST 標準仕様は存在していません。そのため JavaScript のコードから生成される AST はパーサによりさまざまです。

しかしすべてのパーサが思い思いに AST を生成してしまっては相互運用性がなくあまりにも不便です。この課題を解決するため、オープンソースで公開・管理されている JavaScript の AST の仕様が ESTree です。eslint や prettier などメジャーなツールの多くはこの ESTree 互換の AST を解釈するようできており、ESTree にある程度準拠した AST を出力するパーサを各自利用しています。

ただ、ESTree はあくまでもツールやパーサのメンテナーが中心となってツール間の相互運用性を高めるために管理しているルールでしかなく、準拠しないといけない仕様のようなものではありません。実際いくつかのパーサやツールは問題の起きない範囲で ESTree を拡張・改変して利用しています。またまったく ESTree 互換ではない AST を生成・利用するツールももちろん存在します。TypeScript の Compiler は型情報を含んだ独自の AST を生成しますし、後発の Linter/Format ツールである Biome や Oxc などは内部で独自の構文木を利用しています。
